# Оптимизация квалификаций GOVFOR

База изменений: `7a04d2acfd` (master после хотфикса #485). Ветка: `codex/govfor-performance`.
Проверки выполнены локально 5–6 октября 2026 года. На работающий сервер изменения не устанавливались.

## Исправленные источники нагрузки

- `SynchronizeRolePolicy()` больше не сортирует список профессий при каждом запросе допуска.
  Общая политика пересобирается после изменения версии хранилища, режима, исходного override
  или перезагрузки прототипов.
- `SendPolicy()` проверяет версию, доступность хранилища, режим, fail-open, полномочия текущей
  сессии и исходные требования до создания сетевого сообщения. Неизменившиеся политики
  не создают словари допуска, копии требований и строковую подпись. Принудительный запрос
  клиента всегда обслуживается; новая сессия с тем же UUID получает свою политику.
- `IsJobAllowed()` возвращает только результат проверки допуска. Список объяснений по-прежнему
  доступен через `CanTakeJob()`, но не создаётся при массовом опросе.
- `RecordSnapshot()` фильтрует историю до глубокого копирования: только выбранный игрок,
  разрешённые заметки/приостановки и последние 100 подходящих записей аудита для управления.
  Независимость изменяемых коллекций сохранена; чужая история не передаётся.
- Получение одной записи игрока, названия квалификации, аккредитации или инициатора
  приостановки больше не копирует всю базу.
- Статистика вычисляется один раз для опубликованной версии хранилища и выдаётся отдельным
  словарём каждому получателю. Слабая ссылка не удерживает старую базу в памяти после замены.
- Выдача квалификаций, запись участия и Execute миграции начинают копирование в фоновой задаче.
  Порядок игрового запроса сохраняется существующей очередью; блокировка изменений, CAS,
  атомарная запись и публикация только после успешного сохранения сохранены.
- Черновик изменения копирует индекс игроков, но глубоко копирует только изменяемую историю.
  Неизменённые истории используются совместно как неизменяемые данные. Определения,
  аккредитации, приостановки и прочие изменяемые метаданные по-прежнему копируются.
  ResetRecruit также получает собственную копию истории; неудачная запись не меняет
  уже опубликованные данные. Формат канонического состояния не изменён.
- PostgreSQL/SQLite при обычном обновлении читают JSON только при новой ревизии. Проверка
  ревизии и выбор тела выполняются одним SQL-запросом; отсутствие строки считается ошибкой,
  а восстановление связи на той же ревизии восстанавливает доступность.
  Инициализация схемы выполняется один раз на экземпляр репозитория. SQLite больше не
  захватывает write-транзакцию для обычного чтения.
- Обновление списка игроков открытых досье сравнивает повторно используемые записи без
  сортировки UUID и больших строк. Буфер завершённых запросов имён также используется повторно.
  Закрытые/удалённые bound-окна удаляются из списка получателей обновлений.

состояние. Общие паузы GC не исключены переносом операций в фон.

## Выборочное сохранение PostgreSQL и SQLite

После отдельного разрешения пользователя реализован второй этап:

- Полное каноническое состояние, проверка ожидаемой версии (CAS), проекции и аудит
  записываются в одной транзакции. Публикация памяти происходит после commit.
- Изменённые истории определяются по владению копией игрока. Неизменённые истории
  сохраняют прежнюю ссылку; копирование через `Player()` обязательно перед изменением.
- Проекции игроков, выдач и прогресса обновляются только для изменённых игроков.
  Очистка старого прогресса также ограничена этими UUID.
- Аккредитации сравниваются по значению, включая содержимое набора специальностей.
  Записываются только изменённые аккредитации. Приостановки обновляются для затронутого игрока.
- Заметки и аудит добавляются только из нового хвоста списков. Существующий аудит
  остаётся неизменяемым; ограничения и триггеры базы сохранены.
- Небольшие определения, правила ролей, настройки и маркеры миграций сохраняются полностью:
  это сохраняет в проекциях факты, повторно полученные из прототипов.
- PostgreSQL отправляет команды пакетами до 256 команд вместо обмена на каждую строку.
  SQLite сохраняет существующее повторное использование параметров команды.
- Полный `Save()` сохранён для инициализации и совместимости. Репозитории без расширения
  выборочной записи продолжают использовать прежний контракт.

Локальный отдельный прогон: 5000 игроков с одним пунктом прогресса, заметкой и записью
аудита у каждого. Ниже одна выборочная операция Complete и одна последующая полная
запись на той же базе; полная запись PostgreSQL уже использует пакетную отправку.

| Движок | Повторная полная запись | Выборочная операция Complete |
| --- | ---: | ---: |
| SQLite | 441,803 мс | 67,662 мс |
| PostgreSQL 18, loopback | 914,195 мс | 153,658 мс |

Это разные операции на одном масштабе данных, а не статистический серверный benchmark.
Время Complete включает сервисное копирование, аудит и запись. Значения зависят
от прогрева и компьютера; задержка удалённого PostgreSQL не моделировалась.

В новых интеграционных сценариях триггеры запрещают даже попытку вставки/изменения/удаления
проекций постороннего игрока. PostgreSQL дополнительно запрещает повторную вставку старого
ID аудита. Проверены исправление прогресса без удаления чужого, ошибка после начала
изменений с откатом состояния/проекций/аудита/кеша, восстановление после ошибки, конфликт
двух сервисов, сброс рекрута с отзывом аккредитации и разрешением приостановки, участие,
миграция и сохранность полного состояния после перезапуска на обоих движках.

Остаточная стоимость: каждое изменение сериализует и сохраняет полное каноническое
состояние, а черновик копирует индекс игроков и метаданные. Это выполняется вне игрового
потока, но всё ещё создаёт нагрузку на CPU, базу и GC. Следующее архитектурное изменение
потребует независимого восстановления состояния из нормализованных таблиц и отдельного
перехода формата хранения. Эти изменения формат хранения не меняют.

В живой сервер изменения не устанавливались; утверждать конкретное улучшение TPS
или исчезновение пауз GC без повторного профиля на рабочей нагрузке нельзя.
